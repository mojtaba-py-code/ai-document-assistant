# Chapter 9 — Shipping it (Levels 33–36)

## Level 33 — Docker security

**Files.** `Dockerfile`, `.dockerignore`, `compose.yaml`, `deployment/compose/*.yaml`,
`deployment/postgres/`, `deployment/redis/redis.conf`, `scripts/generate-secrets.sh`.

**Image.** Multi-stage build on a digest-pinned `python:3.12-slim-bookworm`; dependencies
installed from a hash-pinned requirements export of `uv.lock` (`--require-hashes`), the
wheel installed with `--no-deps`; runtime without compilers or pip; setuid/setgid bits
stripped; non-root uid/gid 10001; `HEALTHCHECK`; production is the default environment;
optional `WITH_OCR` build argument.

**Compose.** Every application container is `read_only` with a tmpfs `/tmp`,
`cap_drop: [ALL]`, `no-new-privileges`, non-root, pid/memory/CPU limits and health checks.
Secrets are Docker secret files (`DOCASSIST_*_FILE`), generated by
`scripts/generate-secrets.sh` (never printed, never overwritten). Networks: `backend` is
internal (PostgreSQL, Redis, Qdrant, ClamAV), only the API publishes a port (on 127.0.0.1),
only the API and worker can egress. PostgreSQL uses SCRAM and data checksums with three
roles created at init; Redis loads an ACL file (hashed password, dangerous commands removed).
Profiles add ClamAV, Qdrant and a local Ollama model; `deployment/compose/anthropic.yaml`
switches to Claude and `production.yaml` shows production-safe settings.

**Security review**

| | |
|---|---|
| Attack surface | images, container runtime, inter-service network |
| Threats | vulnerable packages, container breakout, lateral movement, secret leakage in images/env |
| Controls | minimal pinned images, non-root, read-only, dropped capabilities, network segmentation, file secrets |
| Weaknesses | Docker's default seccomp blocks the sandbox's network namespace (network isolation relies on segmentation) |
| Improvements | custom seccomp profile or gVisor runtime for the worker |
| Tests | `tests/unit/test_deployment_config.py` (hardening assertions); Trivy scan in CI |

## Level 34 — CI/CD security

**Files.** `.github/workflows/ci.yml`, `.github/workflows/codeql.yml`,
`.github/dependabot.yml`, `.github/gitleaks.toml`, `.pre-commit-config.yaml`, `Makefile`.

**Jobs.** lint (ruff) · type check (mypy strict) · architecture contracts (import-linter) ·
tests on Python 3.12 and 3.13 with PostgreSQL 16 + pgvector and Redis service containers ·
security (bandit, pip-audit on the hash-pinned export) · secret scan (gitleaks) · deployment
config (shellcheck, `docker compose config` for every override, `kubectl kustomize`) ·
container (build, compose smoke test, SPDX SBOM, Trivy with a HIGH/CRITICAL gate) · CodeQL.

**Supply-chain hygiene.** Every action pinned by commit SHA; `permissions: contents: read` at
the top and elevated per job only where needed; `persist-credentials: false`; no secrets in
workflow files; Dependabot for `uv`, GitHub Actions, Docker and Compose, grouped weekly.
Dependency update strategy: bounded ranges in `pyproject.toml`, exact versions in `uv.lock`,
weekly grouped patch/minor PRs gated by the full CI, majors reviewed individually.

**Security review**

| | |
|---|---|
| Attack surface | workflows, actions, dependencies, build cache |
| Threats | malicious actions/packages, secret exfiltration from CI, unreviewed updates |
| Controls | SHA pins, least-privilege tokens, lock file with hashes, scanners, Dependabot |
| Weaknesses | pinned actions still need periodic review of their own dependencies |
| Improvements | signed images (cosign) and provenance attestations (SLSA) on release |
| Tests | the CI itself; `test_deployment_config.py` asserts SHA pins and permissions |

## Level 35 — Production deployment architecture

**Files.** `deployment/kubernetes/` (namespace with the *restricted* Pod Security Standard,
service account without token automount, ConfigMap, ExternalSecret, PVC, API and worker
Deployments, Service, default-deny NetworkPolicies with explicit allows,
PodDisruptionBudgets, HPAs, migration Job, optional HTTPRoute), `deployment/nginx/`,
`deployment/postgres/backup/`, `docs/operations.md`.

**Topology.** Ingress/gateway terminates TLS → API pods (stateless, HPA on CPU) → managed
PostgreSQL (TLS `verify-full`, PITR) and Redis; worker pods scale on queue depth; object
storage for encrypted blobs; egress only to the configured LLM/embedding hosts. Migrations
run as a one-shot Job with the owner DSN only. Pods: `runAsNonRoot`, read-only root
filesystem, `allowPrivilegeEscalation: false`, all capabilities dropped,
`seccompProfile: RuntimeDefault`, secrets mounted as files with minimal keys per pod.

Backup, restore, retention, key rotation and incident response are in
[operations.md](../operations.md).

**Security review**

| | |
|---|---|
| Attack surface | ingress, pods, service accounts, secrets, egress |
| Threats | lateral movement, secret exposure, unbounded egress, noisy neighbours |
| Controls | PSS restricted, NetworkPolicies, no SA tokens, ExternalSecrets, HPA/PDB |
| Weaknesses | managed-service configuration (TLS, backups) is outside the repository |
| Improvements | policy engine (Kyverno/Gatekeeper) enforcing the same rules cluster-wide |
| Tests | `kubectl kustomize` in CI; restore drill (`make restore-drill`) |
